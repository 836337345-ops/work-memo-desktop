# V2.11 Windows 0.1.1 发布任务卡

## 一、授权、基线与分级

- 用户已明确确认 V2.11 功能通过并授权打包，版本号确认为 `0.1.1`。
- 发布基线：`e9b8c1baeb8f6ccd8116998d15e09b363a8b474d`（V2.11 用户验收后的 `integration/v2`）。
- 任务分级：发布任务；执行可见打包任务、PM 审查集成、固定提交独立发布 QA，全部通过后由 PM 将 `integration/v2` 快进合入 `main`。
- 不上传、不推送远程、不发布到网络，不自动安装，不删除旧安装包、工作树或用户数据。

## 二、发布内容

1. 将应用版本从 `0.1.0` 一致更新为 `0.1.1`，仅修改现有版本声明和对应锁文件记录。
2. 生成 Windows x64 NSIS 安装包：`工作备忘录_0.1.1_x64-setup.exe`。
3. 保留旧的 `工作备忘录_0.1.0_x64-setup.exe`，不得覆盖或删除。
4. 新安装包继续使用现有应用标识、数据目录和升级路径；不得改变数据库、备份、导出或自启动业务实现。
5. 安装包继续保持未签名状态；如工具要求证书、付费服务或外部发布，立即停止并报告。

## 三、允许修改范围

- `package.json`、`package-lock.json` 中的项目版本。
- `src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 中的工作备忘录项目版本。
- `src-tauri/tauri.conf.json` 中的应用版本。
- `docs/RELEASE-V2.11.md` 发布候选报告。
- 构建产生的 `src-tauri/target/release` 与 NSIS 安装包不纳入 Git。

## 四、禁止事项

- 不修改任何业务组件、样式、测试逻辑、公共契约、权限、插件、数据库结构或用户数据。
- 不修改应用标识、产品名称、安装模式、安装目录规则或签名配置。
- 不自动运行安装程序，不卸载或替换用户当前安装版。
- 不操作 `main`、不推送远程、不清理旧文件；集成和 `main` 合入由 PM 完成。

## 五、打包与验证

1. 先运行 `scripts/setup-codex-worktree.ps1`，核对发布分支、基线和共享依赖。
2. 用 `apply_patch` 更新版本，确认差异严格限于允许范围。
3. 执行 `npm run build`、`cargo test --manifest-path src-tauri/Cargo.toml`，不重复已经在固定业务提交上通过的完整前端测试。
4. 执行正式 `npx tauri build` 生成 NSIS 安装包；不得使用调试标识或覆盖配置。
5. 记录安装包绝对路径、文件大小、SHA-256、Windows 文件版本、签名状态和构建警告；确认旧 `0.1.0` 安装包仍存在。
6. 提交版本文件和 `docs/RELEASE-V2.11.md`，保持源码工作区干净；安装包作为本地构建产物保留。

## 六、停止与交付

- 遇到版本不一致、安装包缺失、构建失败、旧包被覆盖、签名或网络依赖阻断时停止并报告，不自行绕过。
- 完成后回报正式任务 ID、工作树、分支、提交号、安装包路径、大小、SHA-256、签名状态、验证结果和遗留限制。

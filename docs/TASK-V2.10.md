## 二、用户确认的最终需求

1. 事项列表默认继续按截止日期正序排列：较早日期在前，未设日期最后；同一天按创建时间从新到旧。
2. 事项卡第一行保留展开图标、状态灯、状态选择和“修改编辑”等必要操作；主要文字依次显示“日期  |  事项类别  |  事项标题”，三项字号均与原事项标题一致。第二行显示完整最新进度。
3. 左侧状态、时间、分类筛选组和事项卡统一使用附件所示的“双横线＋箭头”展开/收起图形：向下表示可展开，向上表示可收起。图标应采用适合界面的透明、清晰、可缩放实现，不直接使用 480 像素原图占位。
4. 每次进入程序默认显示工作日历页面；从日历关闭或跳转后仍按既有逻辑返回事项工作台。
5. 左栏顶部快捷入口依次为“工作日历”“进行中”“全部”；原“显示进行中工作”改为“进行中”，原“显示全部”改为“全部”。“工作日历”按钮始终使用较深的绿色底色，并保持文字清楚可读。
6. 修复事项卡展开后新增、填写跟进清单出现“保存失败，请重试”且提示持续不消失的问题。有效跟进内容必须能正常保存；保存成功后卡片内和页面级旧错误都应消失。真实保存失败时不得伪装成功，用户仍可修改后重试。
7. 工作日历的“周一～周日”表头与下方日期数字统一右对齐；各列视觉起点一致。

- 若跟进保存缺陷确实位于现有后端更新实现，可修改对应事项更新模块及其测试，但不得改数据库结构、迁移、备份格式或公共接口；发生这种情况必须先向 PM 报告后再继续。

## 四、禁止修改范围

- 不修改 `src/types.ts`、`src/api.ts`、`docs/CONTRACT.md` 等公共契约；如发现必须修改，立即停止扩展并报告 PM。
- 不修改数据库结构、迁移、备份/恢复格式、安装包配置或版本号。
- 不重新打包，不合入 `main`，不上传或发布。
- 不读取正式用户数据，不清理任何旧工作树、分支、备份或缓存。
- 不顺手调整未列入本卡的样式、交互或数据保护行为。

## 五、实现与异常边界

- 图标须保留按钮的可访问名称、键盘操作与 `aria-expanded` 状态。
- 默认进入日历不应改变现有筛选数据；离开日历后仍可使用“进行中”“全部”和各筛选组。
- 排序规则只需保持并增加必要回归测试，不因界面重排改变数据顺序。
- 跟进清单不得因刚创建的空输入项产生永久错误状态；有效内容保存失败时保留用户输入，后续成功保存必须清除旧错误。
- 所有自动化测试只使用隔离的虚构数据；不得连接或复制正式应用数据。

## 六、必须验证的验收条件

1. 补充或更新事项卡、左栏、应用入口、日历和排序相关组件测试。
2. 为新增跟进清单失败场景增加可复现的回归测试，覆盖失败后可继续输入/重试及成功后错误清除。
3. 执行相关测试、完整 `npm test` 和 `npm run build`。
4. 若修改 Rust，再执行 `cargo test --manifest-path src-tauri/Cargo.toml`。
5. 做一次短时界面检查：启动默认日历、深绿按钮、快捷入口顺序与文案、两种图标方向、事项卡两行布局、日历右对齐、跟进新增保存。

## 七、交付格式与停止条件

- 开发员必须在独立工作树和独立分支完成，先运行 `scripts/setup-codex-worktree.ps1` 并核对固定基线。
- 完成后回报：正式任务 ID、工作树、分支、提交号、修改范围、相关测试、完整测试、构建、短时界面检查、遗留问题和未提交文件。
- 业务修改提交后工作区必须干净。
- 达到上述开发交付即停止；不得创建安装包、合入 `main`、启动长驻调试程序或自行开启 QA。

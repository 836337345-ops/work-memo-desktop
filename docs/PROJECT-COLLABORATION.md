# 工作备忘录项目协作规则

## 一、目标

通过“总 PM + 独立开发员 + 独立测试员”的方式持续开发工作备忘录。聊天历史只作为补充信息，Git、公共契约、任务卡、测试报告和交接快照才是项目事实来源。

## 二、固定角色

### 总 PM

- 与用户确认需求、优先级、边界和验收标准。
- 建立版本基线、任务卡和集成分支。
- 创建用户可见的独立开发任务与测试任务，并检查它们是否真正启动。
- 审查提交、协调公共接口、集成代码、处理冲突和固定测试版本。
- 不承担完整业务功能开发，不用隐藏子任务冒充开发员窗口。

### 开发员

- 一人一条分支、一份工作树，只修改任务卡列出的文件或模块。
- 开始前确认基线提交并运行工作树依赖脚本。
- 发现必须越界或修改公共契约时停止扩展，先报告 PM。
- 完成后提交代码，报告提交号、实际测试、遗留问题和未覆盖范围。

### 独立测试员

- 在 PM 指定的唯一集成提交上测试，不接受“最新分支”等模糊版本。
- 使用隔离的虚构数据，不接触正式用户数据。
- 只修改测试文件和 QA 报告，不修改业务代码。
- 缺陷必须说明复现条件、预期结果、实际结果和影响范围；修复后重新复测。

## 三、任务卡必填内容

每张任务卡必须包含：

1. 版本号和固定基线提交。
2. 功能目标及用户可见结果。
3. 允许修改范围和明确禁止修改范围。
4. 依赖的公共类型、接口和其他任务。
5. 正常流程、异常流程和数据安全要求。
6. 必须执行的测试及验收条件。
7. 交付格式：分支、提交号、自测结果、遗留问题。

## 四、标准协作流程

```text
用户确认需求
    ↓
PM 固定基线并发布任务卡
    ↓
多个可见开发任务在独立工作树并行开发
    ↓
PM 审查提交并集成
    ↓
独立测试员测试固定集成提交
    ↓
缺陷退回原开发员 → PM 再集成 → 测试员复测
    ↓
启动调试版供用户验收
    ↓
用户明确“确认通过，可以打包”后才打包和处理 main
```

## 五、Git 与工作树规则

- 日常开发分支不得直接建立在 `main` 上；由 PM 指定集成基线。
- 新工作树先运行：

  `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\scripts\setup-codex-worktree.ps1`

- 脚本将依赖与编译缓存放到共享位置，避免每个工作树重复占用 C 盘空间。
- 开发员不得切换或写入其他人的工作树，也不得删除其他分支。
- PM 集成优先使用明确提交号，不凭任务标题或口头描述合并。
- 未提交修改、游离提交和测试报告必须先确认归属；未经用户确认不得清理。

## 六、测试门槛

- 普通前端改动：相关组件测试、`npm test`、`npm run build`。
- Rust、SQLite、备份或恢复改动：再执行 `cargo test --manifest-path src-tauri/Cargo.toml`。
- 测试员必须记录被测提交、通过数量、失败数量、数据边界和未测范围。
- 自动测试通过不等于桌面验收完成。窗口尺寸、Windows 缩放、实际点击流程和重启持久化需要在调试版中单独确认。
- 不得把无法执行的检查写成已通过。

## 七、发布与数据安全

- 默认只交付开发/调试模式。
- 用户没有明确说“确认通过，可以打包”时，禁止生成安装包、合入 `main`、上传或发布。
- 备份、恢复、迁移和状态清理必须先验证失败时不会损坏原数据。
- 工作树清理、分支删除、覆盖数据等操作属于独立任务，必须先列出目标和风险并由用户确认。

## 八、上下文与交接

- 每个大版本结束后创建 `docs/HANDOFF-版本号.md`，记录代码锚点、测试结论、未完成事项、工作树状态和下一步。
- 新 PM 对话只读取 `AGENTS.md`、最新交接快照、公共契约和最新用户需求；不复制全部历史聊天。
- 若聊天开始混淆版本、角色或已确认需求，应停止新增开发，先刷新交接快照，再切换新 PM 对话。
- 旧 PM 对话在新窗口接管后保留为只读参考，不继续并行指挥同一版本。

## 九、新 PM 接管检查表

- 当前分支和提交是否与交接快照一致。
- 工作区是否干净，是否存在未提交修改。
- 哪些开发提交已经集成，哪些只是独立分支。
- 最近一次 QA 测试的准确提交和未测范围。
- 是否存在正在运行的调试程序或占用数据目录的第二实例。
- 用户最新需求是否已确认，是否需要新版本基线和任务卡。

未完成以上检查前，新 PM 不应直接开发或清理文件。

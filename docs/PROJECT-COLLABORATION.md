# 工作备忘录项目协作规则

## 一、目标

通过“总 PM + 独立开发员 + 独立测试员”的方式持续开发工作备忘录。聊天历史只作为补充信息，Git、公共契约、任务卡、测试报告和交接快照才是项目事实来源。

## 二、固定角色

### 总 PM

- 与用户确认需求、优先级、边界和验收标准。
- 建立版本基线、任务卡和集成分支。
- 创建用户可见的独立开发任务与测试任务，并检查它们是否真正启动。
- 审查提交、协调公共接口、集成代码、处理冲突和固定测试版本。
- 不承担完整业务功能开发，不用隐藏子任务冒充开发员窗口。
- 不运行长驻调试服务，不连续轮询任务，不在开发员和测试员之外重复执行完整验证。

### 开发员

- 一人一条分支、一份工作树，只修改任务卡列出的文件或模块。
- 开始前确认基线提交并运行工作树依赖脚本。
- 发现必须越界或修改公共契约时停止扩展，先报告 PM。
- 完成后提交代码，报告提交号、实际测试、遗留问题和未覆盖范围。

### 独立测试员

- 在 PM 指定的唯一集成提交上测试，不接受“最新分支”等模糊版本。
- 使用隔离的虚构数据，不接触正式用户数据。
- 只修改测试文件和 QA 报告，不修改业务代码。
- 缺陷必须说明复现条件、预期结果、实际结果和影响范围；修复后重新复测。
- 首次 QA、缺陷复测和用户反馈复测默认在同一测试任务中完成，每轮只更新固定测试提交。独立性来自测试员与开发员分离，不来自不断创建新窗口。

## 三、任务卡必填内容

每张任务卡必须包含：

1. 版本号和固定基线提交。
2. 功能目标及用户可见结果。
3. 允许修改范围和明确禁止修改范围。
4. 依赖的公共类型、接口和其他任务。
5. 正常流程、异常流程和数据安全要求。
6. 必须执行的测试及验收条件。
7. 交付格式：分支、提交号、自测结果、遗留问题。
8. 停止条件：本轮完成到哪一步即结束，以及不得顺手扩展的事项。

## 四、需求变更规则

- 新反馈必须先判断为“新增、修改、取消”中的一种，并写入当前版本最终需求。
- 新要求替换旧要求时，直接更新当前有效规则；任务卡不得继续引用被替代内容。
- 会扩大范围或改变数据行为的反馈，必须由用户确认后再续派；不能静默混入正在测试的版本。
- QA 或审查中发现的可选改进先记入待办，未经用户确认不得由 PM 自行实现或追加复测。
- PM 在连续多轮调整后必须重新输出一次完整的当前版本需求，由用户确认后再继续开发。

## 五、任务分级

- 微调：纯文案、颜色、间距或单组件布局，不涉及业务逻辑、数据和公共契约。使用一个可见开发任务，完成相关测试、构建和 PM 审查，不默认单开 QA。
- 普通功能：涉及交互、状态或多组件联动，执行开发、集成和独立 QA。
- 数据安全：涉及 SQLite、迁移、备份、恢复、删除或真实数据边界，执行完整流程和 Rust 测试。
- 发布：涉及安装包、`main`、上传或发布，须等待用户明确授权。已通过同一业务提交独立 QA 的版本，发布任务只核验版本声明、候选包、哈希、签名和安装边界，不重复完整业务测试；只有候选包或版本文件发生超出任务卡范围的变化，才新增独立发布 QA。

## 六、标准协作流程

```text
用户确认需求
    ↓
PM 固定基线并发布任务卡
    ↓
多个可见开发任务在独立工作树并行开发
    ↓
PM 审查提交并集成
    ↓
独立测试员测试固定集成提交（微调不适用）
    ↓
缺陷退回原开发员 → PM 再集成 → 测试员复测
    ↓
启动调试版供用户验收
    ↓
用户明确“确认通过，可以打包”后才打包和处理 main
```

PM 只在以下四个节点刷新项目状态：任务启动、开发提交、固定集成、独立 QA。等待任务使用一次带游标的长等待，不短间隔轮询；无状态变化不重复汇报。PM 只审查差异、冲突和任务边界；已有可信的开发自测或独立测试证据时，不重复完整测试链路。

## 七、版本阶段锁与实时任务表

每个版本只能处于以下一个阶段：

1. 需求整理
2. 用户确认
3. 开发中
4. PM 集成
5. 独立测试
6. 用户调试验收
7. 等待打包授权
8. 已交付

阶段不可跳过。测试期间不得继续向固定测试提交加入其他功能；测试失败必须退回原开发员，修复集成后重新指定测试提交。

微调不单开 QA 时，独立测试阶段记为“不适用”，并记录开发自测与 PM 审查结果。

`docs/ACTIVE-VERSION.md` 是开发期间的实时任务总表。每个版本必须先登记唯一开发任务和唯一 QA 任务；每张任务记录任务卡、窗口名称、正式任务 ID、工作树、分支、基线提交、当前固定提交、状态、已完成、正在做、下一步、未提交文件和交付提交。被替代任务另列为“停用”，不得继续收发开发或测试指令。

只有同时满足以下条件，PM 才能把任务标为“已启动”：

- 正式任务 ID 可读取并可继续发送消息。
- 工作树、分支和基线正确。
- 依赖预检通过。
- 开发员已发出第一条实际进度。
- 与其他任务的修改范围不存在未协调重叠。

只获得临时任务编号、只创建了目录或只写了任务卡，都不等于任务已经启动。

若创建后暂未能读取正式任务 ID，PM 先等待一次并再次读取同一任务；ID 可读取且可继续发送消息时，应更正为已启动，不得因此新建重复任务。若分支、基线或依赖异常，记录为环境阻断，修复后续用原任务和工作树。

### 任务创建防重复流程

1. 创建前检查实时表、任务列表和工作树，确认同版本同角色没有可恢复任务。
2. 发出创建请求后，立即在实时表登记“创建中”、临时标识、目标角色和预期分支。
3. 只进行一次带游标等待，然后重新读取任务列表、正式 ID 和工作树；回调未返回不等于任务未创建。
4. 原任务可读取或工作树已经产生时，继续原任务并完成启动验真；不得再次创建。
5. 原任务确实无法读取、无法发送消息或工作树损坏时，先记录证据并把它标为“停用”，然后最多创建一个替代任务。
6. 替代任务启动后，将正式 ID 写入唯一任务登记；其他临时或重复窗口一律标为“停用”，不再发送消息。

测试发现需求口径冲突时，暂停测试并由 PM 修正当前任务卡或公共契约；修正后回到原 QA 任务复测，不以“全新测试员”解决文档冲突。

## 八、Git 与工作树规则

- 日常开发分支不得直接建立在 `main` 上；由 PM 指定集成基线。
- 新工作树先运行：

  `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\scripts\setup-codex-worktree.ps1`

- 脚本将依赖与编译缓存放到共享位置，避免每个工作树重复占用 C 盘空间。
- 开发员不得切换或写入其他人的工作树，也不得删除其他分支。
- PM 集成优先使用明确提交号，不凭任务标题或口头描述合并。
- 未提交修改、游离提交和测试报告必须先确认归属；未经用户确认不得清理。

## 九、依赖与磁盘预检

每个新工作树开始前必须确认：

- `node_modules` 已正确连接到共享依赖，前端测试命令可以启动。
- Rust `target` 使用共享编译缓存，避免在每个工作树重复构建。
- 工作树位于任务卡指定基线，分支名称正确。
- C 盘和共享缓存所在磁盘有足够空间继续编译和测试。
- 不存在另一个程序实例占用相同测试数据目录。

任一检查失败时，将任务标记为“环境阻断”并先报告 PM；不得一边报错一边开始修改代码。每个版本独立测试通过后，PM 输出工作树和缓存清理候选，用户确认后才执行清理。

任务 ID、依赖脚本、缓存或工作树故障应作为独立的基础设施问题处理。修复后恢复原业务任务，不把故障恢复、功能集成和 QA 混在同一个 PM 长回合，也不重复创建已存在的任务。共享 Rust `target` 通过工作树目录链接复用；不得仅因未设置单独环境变量就误判依赖故障。

## 十、测试门槛

- 微调：相关组件测试和 `npm run build`。
- 普通功能及更高风险前端改动：相关组件测试、`npm test`、`npm run build`。
- Rust、SQLite、备份或恢复改动：再执行 `cargo test --manifest-path src-tauri/Cargo.toml`。
- 测试员必须记录被测提交、通过数量、失败数量、数据边界和未测范围。
- 自动测试通过不等于桌面验收完成。窗口尺寸、Windows 缩放、实际点击流程和重启持久化需要在调试版中单独确认。
- 不得把无法执行的检查写成已通过。
- PM 在固定集成提交上只执行一次与风险相称的检查；已有可信测试证据时不重复完整链路。
- 调试程序完成短时启动验证后记录 PID、隔离数据目录、固定提交和结果并结束任务。用户人工验收时单独启动，不让 PM 等待。

## 十一、发布与数据安全

- 默认只交付开发/调试模式。
- 用户没有明确说“确认通过，可以打包”时，禁止生成安装包、合入 `main`、上传或发布。
- 备份、恢复、迁移和状态清理必须先验证失败时不会损坏原数据。
- 工作树清理、分支删除、覆盖数据等操作属于独立任务，必须先列出目标和风险并由用户确认。

## 十二、中断恢复

- 开发员每完成一个可独立验证的小阶段就提交一次，避免长时间只保留未提交修改。
- 开始长时间构建或测试前，先确认当前修改已安全保存。
- 每次进度更新同步写明“已完成、正在做、下一步、未提交文件”。
- 额度耗尽、电脑重启或窗口异常后，PM 先读取 `docs/ACTIVE-VERSION.md`、任务窗口状态和工作树 Git 状态，再决定续派。
- 原窗口可恢复时继续原窗口；无法恢复时才建立接管窗口，并要求新窗口先核对旧工作树，不得从头重做或制造重复分支。
- PM 不得把自己运行的检查当作开发员交付或独立测试结果。

## 十三、上下文与交接

- 普通功能及更高风险版本结束后创建 `docs/HANDOFF-版本号.md`，记录代码锚点、测试结论、未完成事项、工作树状态和下一步。
- `PROJECT-HANDOFF.md` 只记录长期产品事实、数据边界和稳定执行规则；`ACTIVE-VERSION.md` 是唯一当前版本、阶段、固定提交、阻断项和下一步来源。历史细节保留在对应任务卡、QA 与版本交接文件中。
- 当前事实的优先级为：用户已确认的当前任务卡 → `ACTIVE-VERSION.md` 当前轮次 → `CONTRACT.md` 当前公共规则 → 历史交接与旧 QA。历史记录不得覆盖前三项。
- 新 PM 启动只读取 `AGENTS.md`、`docs/PROJECT-HANDOFF.md`、`docs/ACTIVE-VERSION.md`、当前额度审计和 Git 状态。公共契约、QA 报告及本文件按当前任务需要再读，不复制完整历史聊天。
- 若聊天开始混淆版本、角色或已确认需求，应停止新增开发，先刷新交接快照，再切换新 PM 对话。
- 旧 PM 对话在新窗口接管后保留为只读参考，不继续并行指挥同一版本。

## 十四、版本完成定义

版本标记“完成”前必须同时具备：

- 每张开发任务已提交，交付提交和遗留问题已记录。
- PM 已审查并集成到明确提交，集成工作区干净。
- 相关测试、完整前端测试、构建及所需 Rust 测试通过。
- 任务分级要求独立测试时，测试员已在准确的集成提交上测试并提交 QA 报告。
- 发现的缺陷已退回开发员修复，并按任务分级完成复测。
- 调试版已交给用户，人工验收状态和未测范围已记录。
- 打包和 `main` 状态与用户授权一致。

缺少任何一项时，只能写“开发完成”“自动测试通过”或“等待用户验收”，不能笼统宣布项目已经交付。

## 十五、新 PM 接管检查表

- 当前分支和提交是否与交接快照一致。
- 工作区是否干净，是否存在未提交修改。
- 哪些开发提交已经集成，哪些只是独立分支。
- 最近一次 QA 测试的准确提交和未测范围。
- 是否存在正在运行的调试程序或占用数据目录的第二实例。
- 用户最新需求是否已确认，是否需要新版本基线和任务卡。
- `docs/ACTIVE-VERSION.md` 中的任务 ID、工作树、分支和实际 Git 状态是否一致。

未完成以上检查前，新 PM 不应直接开发或清理文件。
